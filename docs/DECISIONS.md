# Decisions and assumptions

This file records the engineering defaults chosen while implementing SRS v0.1, and the decisions
still open. Assumptions are reversible engineering choices. None of them is product approval, and
none of them changes scope. Scope changes are listed separately and only when the owner asked for
them. Open decisions need an owner before the stage named under "Resolve before".

## Assumptions made during implementation

| ID | Assumption | Why | Reversal cost |
|---|---|---|---|
| A-01 | **minSdk 26 (Android 8.0), target/compile SDK 36.** Proposed answer to D-01. | Gives `java.time` without desugaring, `TYPE_ACCESSIBILITY_OVERLAY`, `AudioFocusRequest`, `onRenderProcessGone` and the WebView APIs the browser needs. | Low: lowering it needs core-library desugaring and API guards. |
| A-02 | **Application ID `app.dereel` is a placeholder** (D-09). | Needed to build. | Free before the first public release. Afterwards it breaks updates. |
| A-03 | **D-04 defaults as proposed.** Blocking on, allowance off until chosen, "Allow shared videos" on, but only effective where the adapter supports it (Instagram inside Dereel). | SRS D-04. | Change the defaults in `PlatformConfig`. |
| A-04 | **Browser recommendation controls default to on** (hide Explore grid, suggested posts, sponsored posts, YouTube home feed, up-next, promoted items). | Matches the product goal of reducing endless feeds. The user can turn each off under More controls. | Change `BrowserControl.defaultsFor`. |
| A-05 | **Temporary access is an app-wide preference, off by default.** It is offered only on block screens and the platform screen. | UX-10 and FR-29 say it appears only when the user enables it. One switch is simpler than one per platform. | Low. |
| A-06 | **Native enforcement: one automatic Back per episode, with a short banner explaining why.** If the surface is still there after the 1 s cooldown **and again 0.5 s later**, a cover with "Go back" replaces further Back actions. At most 3 automatic Back actions per 30 s per platform. | FR-07 and FR-10. Back leaves the user somewhere useful. The confirmation check exists because YouTube keeps Shorts views reported visible briefly after Back (seen on the emulator). | Tune in `DenyEpisodeController`. |
| A-07 | **Covered short videos get transient audio focus**, which asks the app to pause sound behind the cover. | A cover alone can leave audio playing. | Remove `requestAudioFocus()`. |
| A-08 | **Native events are limited to the packages that have a native rule set** (`packageNames` in the service config: Instagram, YouTube and, since S-01, Snapchat and Facebook Lite; `NativeScopeTest` keeps the two lists equal). While a native session or cover is active, a 1 s presence check confirms the app is still in front **and re-runs detection**, so covers clear and usage stops even if the app sends no further events. | SEC-03 and FR-06 "documented package scope"; FR-08 and FR-25. | Medium: widening scope would need a revised disclosure. |
| A-23 | **Anchors are found with in-process view-ID lookup** (`findAccessibilityNodeInfosByViewId`), with a bounded tree walk only as a fallback. Content-change detection is limited to every 500 ms; window-state changes are checked after 40 ms. Scroll events are not subscribed. | Lookups run on the target app's UI thread, so they must be few and infrequent (NFR-05, and not degrading the social app). | Tune constants in `DereelAccessibilityService`. |
| A-09 | **Native detectors read view IDs, visibility and selection only, never text or content descriptions.** The `UiNode` interface has no text field. | SEC-03. It is also language-independent, which helps D-06. | Adding text matching would need a privacy review. |
| A-10 | **Layout recognition is flagged only after two visits in a row, each at least 15 s long with at least 5 snapshots, and with no known anchor seen.** | FR-37 without false alarms when, for example, a user opens straight into a DM thread. | Tune in `LayoutRecognitionTracker`. |
| A-11 | **Usage is attributed by checkpoint deltas.** A midnight split is applied only when wall and monotonic time agree within 2 s and the zone is unchanged. Otherwise observed time stays with its existing day. | FR-28: no negative durations, and no reduction of an existing day. | Documented in `UsageTracker`. |
| A-12 | **Usage history is kept per local-day segment**, so a session crossing midnight becomes two records. | FR-28 "split between days", and simpler day queries. | Schema-level, so it needs a migration. |
| A-13 | **Temporary grants persist across restarts.** Within one boot, expiry uses the monotonic clock. Across a reboot it uses the wall clock (boot detected via `BOOT_COUNT`). | Grants are user-authorized. Losing one on restart would be surprising. The SRS says this is not a tamper-proof clock policy. | Low. |
| A-14 | **Shared exception origin = previous committed route is a conversation, and the transition is user-initiated** (an in-page route change, or a full load following a gesture). A link shared to Dereel through the share sheet is the second supported origin. | FR-20 ("originating conversation or link"). | Narrowing to DMs only is a one-line change. |
| A-15 | **A shared link waiting to open survives sign-in pages only.** Any other route clears it. | So that "open shared link → sign in → see the reel" works without widening scope. | Low. |
| A-16 | **Browser sign-in data is cleared by expiring cookies on the platform's documented domains and deleting site storage for its origins.** Instagram's scope includes facebook.com; YouTube's includes google.com. Both are disclosed. | FR-19. WebView has one shared cookie jar, so one active login per platform is natural (SEC-06: no cookie-slot switching). | Cookies on non-root paths cannot be enumerated, so the UI reports a partial clear when anything remains. |
| A-17 | **Plain HTTP pages never load inside Dereel.** They are offered as external links instead. | SEC-05 and INT-02. | Low. |
| A-18 | **Third-party cookies are on in the WebView** (revised). Originally off. On a Pixel 9, Instagram login inside Dereel repeatedly bounced back from Instagram's login-check page while the same account logged in through Chrome after a CAPTCHA. Login succeeded after two changes: third-party cookies on, and embedded frames allowed to use `about:`, `blob:` and `data:` addresses. **The device log does not show which change was decisive**: the successful login skipped the check page entirely, so Instagram may also simply have stopped asking. Main-frame navigation is still limited to platform and sign-in pages. | FR-18: sign-in must work through the platform's own flow. | Re-test with each change reverted, on an account that still gets the check, before relying on either. |
| A-19 | **Camera, microphone, location, file upload, downloads and pop-up windows are denied in the browser.** | Not first-release features. They would widen the attack surface. | Each needs its own documented, tested exception. |
| A-20 | **Room with an exported schema, and no destructive migration fallback.** `SchemaGuardTest` fails if the version is bumped without a migration. | DATA-01. | Not applicable. |
| A-21 | **Manual dependency injection** (`AppContainer`) instead of Hilt. | Small graph, fewer build-time dependencies. | Low. |
| A-22 | **Status for the native method is also shown to "inside Dereel" users once Accessibility is on**, because the service then enforces in the app too. It is not shown otherwise, so nobody is repeatedly asked to enable an optional feature (UX-11). It is never shown when none of the platform's supported apps is installed. | UX-08 and UX-11. | `StatusEvaluator.methodsToShow`. |
| A-24 | **On Facebook, "short video" means Reels and the Video tab.** Blocked routes: `/reel/…`, `/reels/…`, reel share links (`/share/r/…`) and `/watch` when it does not name one video. A named video (`/watch?v=…`, `/<page>/videos/<id>`) is a regular video. | The request was "add Facebook". Reels are Facebook's short-video feed, and the Video tab is the same kind of endless video feed. If Facebook redirects a named video to a reel page, the reel page is what gets blocked. | Change `FacebookRoutes` and `facebook.js` together (shared fixtures enforce this). |
| A-25 | **Facebook is protected in the Facebook Lite app and inside Dereel. The regular Facebook app is not observed or protected.** In Facebook Lite the only anchor is `video_view`, its full-screen video player, when it fills at least 60% of the window. Any video opened full screen there is treated as a reel. Videos playing inside the feed are not matched. | Facebook Lite draws its own interface and exposes almost no identifiers; the video player is the exception (names-only captures, 20 Nov 2026). Nothing distinguishes a reel from another full-screen video. An earlier note in this file said Facebook Lite could not be supported: that was concluded from its home screen alone and was wrong. | Rule set `fb-lite-native-0.1.0`. The regular app needs its own rule set and package entry. |
| A-26 | **Snapchat works in its app only, and "short video" means Spotlight.** Anchor: `spotlight_container` filling the window. The five `ngs_*_icon_container` tab anchors mark the layout as recognised and are left uncovered. Chats, the camera, the map, Stories and Discover are not blocked. | Snapchat has no mobile website to filter. `opera_viewer` was rejected as an anchor because it is Snapchat's general media viewer. | Rule set `sc-native-0.1.0` in `NativeRules`. See D-12 before relying on it. |
| A-30 | **A platform can have more than one supported app** (`Platform.nativePackages`), each with its own rule set. Text about app protection names the supported app, so Facebook's says "Facebook Lite". "Installed" means at least one supported app is installed, and Open launches the first one found. | The owner asked for both Facebook apps. Only Facebook Lite could be examined, so the model is ready for the second without claiming it. | `Platform.nativePackages`, `NativeRules.all`. |
| A-27 | **A platform with one opening method has it preselected.** (Today that is Snapchat only.) The user is not asked "How should Dereel open…", and the platform screen explains how it opens and why instead of offering a choice. A stored method that is not offered is repaired when settings are read. | UX-03 (one primary Open action) and UX-04. Asking a question with one answer adds a step for nothing. | `Capabilities.methods`, `PlatformConfig.validMethod`. |
| A-28 | **Facebook has no shared-video exception and no "More controls" yet.** A Facebook reel link shared to Dereel is blocked like any other reel. Messages are never treated as a shared-video context. | FR-20 covers the Instagram journey only (D-05). Facebook share links (`/share/r/<token>`) do not name the reel they lead to, so the "one recognised item" rule cannot be checked before loading. | Needs a designed and tested journey first. |
| A-29 | **Signing out of Instagram inside Dereel still clears facebook.com data, so it also signs out of Facebook inside Dereel.** The confirmation says so. Signing out of Facebook leaves Instagram signed in. | FR-19: Instagram can sign in with Facebook, and that session must not survive an Instagram sign-out. | `PlatformWeb.dataScope`, `PlatformWeb.alsoSignedOut`. |
| A-31 | **Where the new time rules sit in the policy order:** temporary access, then the sleep schedule, then an exhausted allowance, then an interval break, then shared items, then a remaining allowance or interval window, then default blocking. The sleep schedule and a break deny shared reels too. | POL-01 gives the original order. The new rules only ever restrict, and POL-04 lets temporary access override blocking because the user asks for it each time. Shared items follow POL-03: they do not outrank a time limit. | `PolicyEngine`, `TimeRulePolicyTest`. |
| A-32 | **Interval timer:** per platform, off by default, shared by the app and inside Dereel. Watch time is counted viewing with blocking on. When the window is used up a break starts; its end is stored as a wall-clock time, never longer than the configured break. A pause as long as a break starts a fresh window. Choices offered: watch 5, 10, 15 or 30 minutes; break 15, 30, 60 or 120 minutes. With a daily allowance set, both apply and the sooner limit wins. With no allowance, the timer alone allows viewing inside its window. | The owner chose "watch a few minutes, then a forced break". Storing the break lets it survive a restart. Capping it stops a clock change from stretching it. | `IntervalSetting`, `PacingTracker`. |
| A-33 | **Sleep schedule:** one schedule for every platform, every day, off by default, 22:00 to 07:00 until changed. It may cross midnight. Equal start and end means it never applies, and Settings says so. | The simplest form of "stricter rules at night". Per-day and per-platform schedules can be added later without changing stored data. | `SleepSchedule`. |
| A-34 | **Protection alert:** off until turned on, and notification permission is asked for at that moment (UX-07). It is posted when app protection that worked before has been off or disconnected for 8 seconds, a selected platform with blocking on has its app installed, and the user asked for alerts. It is withdrawn when protection works again. **It cannot be posted if Android stops Dereel completely**, and Help says so. | The owner's own phone had Dereel's Accessibility access off without any sign of it. The delay avoids alerts while the service restarts. No background job was added, to keep NFR-09 (no periodic wake-ups). | `ProtectionCheck.protectionStopped`, `StatusMonitor`, `ProtectionAlerts`. |
| A-35 | **Live timer:** on by default, with a switch in Settings. In apps it is a small overlay that cannot be touched and is hidden from screen readers (it changes every second). Inside Dereel it replaces the "Inside Dereel" subtitle. It shows whichever runs out first: temporary access, the interval window or the daily allowance; otherwise today's time. | Makes allowed time visible without interrupting. It never appears while content is blocked or on other screens. | `TimerText`, `OverlayController.showTimer`. |
| A-36 | **Database schema 2** adds the interval columns, the sleep, alert and timer preferences and a table for interval progress, through a real migration. Existing rows keep their values. | DATA-01: no destructive upgrade. | `DereelDatabase.MIGRATION_1_2`, `DatabaseMigrationTest`. |
| A-37 | **Interface redesign:** Home has one status card with "Check protection", one compact card per platform with a single Open button and a settings gear, and unadded apps as chips. Settings and platform screens are grouped into a few titled cards. Activity gains a 7-day bar chart, also listed as numbers. Platforms get a coloured monogram: Dereel's own tints, not the platforms' logos (changed by S-04: see A-39). | The owner asked for a better interface. The earlier Home needed long scrolling with four platforms. Brand logos are third-party marks and were not used at the time. | Compose screens under `app/.../ui`. No stored data depends on it. |
| A-38 | **App protection that worked before stays visible after it stops.** For a platform set to open inside Dereel, Home used to show the app's row only while Accessibility access was on. If access was later turned off the row vanished and Home said "Protection is active", while the alert said protection had stopped. Now the row stays as "Needs attention" with a fix button. Access that was never turned on is still not mentioned. A tap on the alert opens Home. Dereel's main screen is `singleTop`, so a second start reuses the open screen. | Found on the emulator on 21 Nov 2026. UX-08: never show successful protection where none exists. **Downside:** someone who turns access off on purpose keeps seeing "Needs attention" for that app; there is no "stop reminding me" choice. | `StatusEvaluator.methodsToShow`, `StatusEvaluatorTest`, `ProtectionAlerts.ACTION_SHOW_STATUS`, `MainActivity`. |
| A-39 | **Platform logos replace the coloured monograms** (S-04) wherever a platform is shown: first-run setup, Home cards and "add" chips, Activity, Settings, the platform screen and Help. The outlines are the Simple Icons glyphs with their path data unchanged (`docs/THIRD_PARTY.md`). Colours: Instagram in its gradient (a five-stop approximation, not an official file), YouTube red with a white triangle, Facebook blue with a white "f", Snapchat's white ghost on its yellow tile. The others sit on a plain tile: white in the light theme, a raised surface in the dark one. A logo is decoration: it is hidden from screen readers and the platform is always named beside it (NFR-03). Figures in Activity keep Dereel's own tints, because the brand colours are not all readable as text. Help ends with a line saying whose trademarks they are. | The owner asked for the logos. Recognising an app by its logo is faster than by a letter. | `PlatformAvatar` and `PlatformLogos.kt` plus four drawables (`ic_logo_*.xml`). Going back to monograms means changing that one composable. **Risk:** the logos are other companies' trademarks, used without asking (D-15). |
| A-40 | **Settings arrangement** (S-04). Five cards: Protection, Your apps, Time, Your data, About. Every row has the same shape (an icon or logo, a title, one line of help, then its control), so text lines up down the screen. **Your apps** is new: one row per platform with a one-line summary of what is switched on ("Blocking Reels · 15 min a day"), opening that platform's screen; platforms not yet added are listed last with "Add". The summary describes saved settings only and never claims that blocking is working, which stays a status question (UX-08). The two sleep times appear under the schedule's switch only while it is on. The three "clear browser data" rows are folded under one "Dereel browser data" row; each is still its own action with its own confirmation (FR-35). "Reset Dereel" is last and marked in the error colour. Accessibility access shows its state as a labelled pill, and "Off" is neutral because app protection is optional (UX-11). The version line moved into the About card. Four help lines were shortened. Removing a platform now closes its screen and returns to the list. | The owner asked for a better-arranged, more seamless Settings screen. On the emulator the old screen was a long list of three-line rows with no visual anchors, and there was no way from Settings to an app's rules. | `SettingsScreen`, `Components.kt` (`ClickRow`, `SwitchRow`, `InfoRow`, `RowIcon`), `AppIcons`, `core/.../RuleSummary` with `RuleSummaryTest`, `PlatformScreen`. The platform screen itself keeps its earlier rows. |

## Scope notes

- Later-scope items (VPN/DNS filtering, AI classification, parental management, cloud sync,
  multiple accounts, subscriptions, background playback, PiP, whole-app blocking, schedules,
  uninstall protection) are not implemented, and no control for them appears in the UI (SRS 2.2).
- Platforms beyond Instagram and YouTube exist only through S-01 above. No other platform has
  been added.
- **Known gap from sharing a browser between platforms:** Instagram's sign-in flow may load
  facebook.com pages. Facebook's short-video routes are refused there and offered as an external
  link instead, but other Facebook pages opened from the Instagram browser load without
  Facebook's page rules, and an in-page move to Reels from such a page is not corrected.
- The `analysis/` folder and `base.apk` in the working directory are SocialLite reference
  material. They were not read during implementation and are excluded by `.gitignore` (SEC-08).
